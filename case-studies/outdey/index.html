01 / The challenge

A single app for a multi-sided event.

Event-goers need fast discovery and trustworthy tickets. Organizers need creation, inventory, buyer visibility, and admission tools. Social features add friends, conversations, notifications, and ticket resale. Those paths share the same event and identity state, so a change in one role must remain coherent everywhere else.

01

Role-aware journeys

The same person may browse as an attendee and manage an event as an organizer. Navigation and actions needed to adapt without fragmenting the product.

02

Transactional state

Ticket types, quantities, purchases, resale bids, payments, and admission status all depend on current server state—not optimistic assumptions.

03

Real-world handoff

The digital journey ends at a physical venue. QR admission had to turn a purchased ticket into a clear, fast check-in action.

02 / Engineering decisions

Keep the event at the center.

As the sole mobile developer, I owned Flutter delivery, production fixes, API extensions, store-review remediation, and release. I connected product flows around durable IDs and server-owned state instead of duplicating business truth in each screen.

Primary decision

Model buyer and organizer actions around one event lifecycle.

Create, edit, discover, purchase, report, review attendees, and scan admission all reference the same event and ticket resources. This keeps role-specific interfaces aligned with the underlying product state.

Live updates

Make social state event-driven.

Firebase events carried conversation, message, friend-request, notification, event, and ticket-resale changes into the relevant mobile journeys.

Product boundary

Separate UI state from API ownership.

The app presents progress and recovery clearly, while the backend validates ownership, quantities, duplicate reports, authentication, and token renewal.

03 / Architecture

From intent to admission.

Feature controllers coordinate the Flutter experience. REST resources own identity, event, and ticket transactions; Firebase carries live social and notification changes; device services complete maps, payment, media, and QR workflows.

04 / Reliability

Design for the unhappy path.

In a transactional event app, failure states are part of the core journey. The interface must explain what happened without implying that a ticket, payment, or check-in succeeded when the server has not confirmed it. Focused unit and widget tests covered selected business rules, controller states, validation, and critical failure feedback.

A

Expired access

Refresh-token handling restores valid sessions or returns the user to authentication instead of leaving protected screens in an ambiguous state.

B

Inventory conflict

Ticket quantity and ownership errors remain server-authoritative, with actionable mobile feedback for unavailable or invalid selections.

C

Event-driven changes

Message, friend, notification, event, and resale updates target the affected resource so screens can refresh the right context.

05 / Product surface

One connected journey.

06 / Result + reflection

A complete event loop, shipped.

The delivered product connects browsing, planning, purchasing, organizer operations, and admission on both mobile platforms. The result is observable in the public releases; no invented engagement or revenue figures are used here.
