01 / The challenge

BLE without a fixed protocol.

Most connected-device apps know their service UUIDs, characteristic formats, and controls before they ship. BlueDash had to work when those details came from the user: scan a device, inspect services, choose characteristics, define byte formats, test operations, and turn the working setup into a reusable dashboard.

01

Arbitrary GATT

The connection layer could not assume one service, characteristic, property, or command protocol.

02

Raw bytes

Readable values and writable commands may be integers, floating point, text, hexadecimal, signed, unsigned, or ordered differently in memory.

03

User-built UI

Buttons, sliders, indicators, and graphs had to store enough metadata to reproduce the correct characteristic operation later.

02 / Engineering decisions

Make behavior data.

The key move was separating BLE transport from dashboard definition. A widget does not hard-code a peripheral command; it carries the metadata needed to resolve a service, characteristic, operation, and codec at runtime.

Primary decision

Represent device controls as reusable metadata.

Persisted dashboard and widget models connect visual controls to UUIDs, properties, encoding rules, ranges, and display behavior. The same renderer can therefore drive different devices.

Protocol boundary

Centralize BLE operations.

Scanning, connection, discovery, read, write, and notify behavior live behind focused data sources, repositories, and use cases instead of inside widgets.

Confidence loop

Test before publish.

A dedicated testing path lets users exercise characteristics and codecs before the configuration becomes a saved or shared dashboard.

03 / Architecture

From GATT to interface.

A feature-first Flutter structure separates presentation, domain use cases, repositories, and BLE data sources. Hive persists devices and dashboard definitions; Firebase supports account and publishing flows.

04 / Reliability

Make uncertainty visible.

BLE is asynchronous and environment-dependent. The experience needs distinct states for permissions, scanning, connection, discovery, operation support, decoding, and notifications so an error can be diagnosed instead of appearing as a frozen control.

A

Permission + radio state

Scanning begins only after the platform-specific permission and Bluetooth prerequisites are satisfied.

B

Capability checks

Controls map to characteristics that actually support read, write, or notify rather than assuming every operation is available.

C

Codec validation

Encoding and decoding are centralized so malformed values can fail at a known boundary before corrupting dashboard behavior.

05 / Product surface

Configure. Test. Control.

06 / Result + reflection

One app, many devices.

BlueDash shipped on iOS and Android as a reusable no-code BLE interface. The technical result is a platform that can discover and operate devices through configuration instead of a separate hard-coded application for each profile.

01

Delivered

Dynamic discovery, configurable codecs, read/write/notify operations, reusable dashboard controls, local persistence, import, and publishing paths. Focused unit and widget tests covered selected byte-conversion logic, persisted configuration behavior, and critical dashboard states.

02

What I would improve next

Version dashboard schemas, add a simulated GATT device for repeatable tests, and expand codec/property coverage with protocol fixtures.

03

Why it matters

It shows BLE engineering as a reusable product system, not a one-device demo.
